# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A production/KPI management system for a furniture manufacturing company (Melores Mebel), built on Trello + a Telegram bot + a web admin panel. Full spec: `Trello_Telegram_TZ_v2.1_ToLiq.docx` / `TZ_content.txt` (Uzbek). Core business goal: automatically detect underperforming employees via per-task KPI penalties, driven off deadlines tracked in Postgres (not Trello itself, which has no timers or automatic labeling). A second, parallel production pipeline ("Fasad sex" / "Nazorat Trello", spec: `Nazorat_Trello_Bot_TZ_v1.2_sxemalar_bilan.pdf`) shares the same engine — see "Fork/join task chains" and "Project status and roadmap" below.

Three parts sharing one Postgres database:
- `bot/` — Python + aiogram v3.22.0. This is where almost all real functionality lives: Telegram bot, Trello sync, timers, KPI/penalty calculation, scheduler. **This is almost always the directory you'll be working in.**
- `web/` — Node/Express admin panel (Phase 4: monthly stats table + Chart.js chart + best/worst ranking, single shared-password login). Deliberately thin — TZ §4 scopes it to "view stats, add employees" only, so complex data-entry flows (task creation, client linking) stay in the Telegram bot's Mini App, not here.
- `shared/db-schema.md` — hand-maintained source-of-truth doc for the DB schema. **Update this whenever you change `bot/db/models/`.**

Only `bot/` (via Alembic) may run migrations. `web/` reads/writes the existing schema but never alters it.

  task no longer flips `OVERDUE` or gets the "deadline near" warning
  (`task_repo._timer_running()`).
- **§5.4** — `app_settings.deadline_warning_hours` (4; was a hardcoded 24)
  and `overdue_repeat_hours` (12, `0` = off) + a repeat-reminder phase in
  `overdue_watch_job`.
- **§7/§8** — `departments.telegram_chat_id` (sex group), `employees.manager_id`

- **§11** — `stats_service.get_order_funnel()` / `get_stage_bottlenecks()` /

## Commands

All commands run from `bot/`, using the venv at `bot/.venv` (already configured as the VS Code interpreter via `.vscode/settings.json`).

```
# Setup
cd bot
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

# Migrations
alembic revision --autogenerate -m "description"
alembic upgrade head

# Run the bot
python main.py
```

Web panel: `cd web && npm install && npm start` (or `npm run dev` for nodemon). Reads the **same root `.env`** as `bot/` (`dotenv.config({ path: '../.env' })`), plus its own `WEB_ADMIN_PASSWORD`/`WEB_SESSION_SECRET` — `server.js` exits immediately at startup if either is unset.

**There is no test framework** — no pytest in `requirements.txt`. `bot/tests/` holds a small number of **plain runnable scripts** instead, each executed directly and asserting with bare `assert`, no fixtures, no DB, no network:

```
# Run one:
.venv/Scripts/python tests/test_trello_board_map.py     # 25 real board list names -> classification
.venv/Scripts/python tests/test_penalty_responsible.py  # who a KPI score is written to (+ penalize_all_assignees)
.venv/Scripts/python tests/test_brigade_membership.py   # brigade auto-linking rules
.venv/Scripts/python tests/test_miniapp_cache_headers.py # Cache-Control on Mini App responses
.venv/Scripts/python tests/test_miniapp_authz.py        # role gate + department scope + initData signature
.venv/Scripts/python tests/test_sla_engine.py           # SPEC.md SLA: per-stage/quota/block, STOP freeze, mebel guards

# Run all (there is no runner — this loop is the whole "test suite"):
for t in tests/test_*.py; do printf "%-42s " "$t"; .venv/Scripts/python "$t" >/dev/null 2>&1 && echo OK || echo FAIL; done
```

Two checks worth running alongside them, since neither is covered by the scripts above and both have broken silently before:

```
.venv/Scripts/python -c "import main"                   # every module still imports (catches missing enum/column wiring)
node --check miniapp/public/js/app.js && node --check miniapp/public/js/i18n.js
```

`i18n.js` has no test — a key added to `uz` but not `ru` renders as the raw key
string for Russian users. Diff the two blocks after touching it.

Follow that shape for anything new here: fake the repositories, keep it importable and runnable on its own. Beyond those, verification is done by writing a one-off script that calls services directly against the **real** Railway Postgres DB and, for Trello-touching work, a real Trello board — never the production **"Fasad seh"** board (see Gotchas below before assuming the "Test" board is a safe target). Pattern used throughout this codebase's history: write a temp `bot/_smoke_<feature>.py` script, run it with `.venv/Scripts/python`, assert expected DB/Trello state, then delete test rows (watch FK ordering — see Gotchas) and delete the script when done. `bot/_seed_demo_data.py` is a **different, standing** script (deliberately *not* prefix-matched or deleted like the `_smoke_*` ones) that populates a full realistic dataset — org structure, multi-stage tasks in every status, KPI history, sales leads — via the real service layer against a **brand-new Trello board it creates itself** (`TrelloClient.create_board`/`create_list`); re-run it any time a fresh demo/walkthrough dataset is needed, but it errors on duplicate names/phones if run twice without clearing prior demo rows first. `bot/_backfill_mebel_trello_tracking.py` is a third category — not one-shot-and-delete like `_smoke_*`, not a standing demo-data seeder like `_seed_demo_data.py`, but a **repeatable rollout-prep** script: idempotent, safe to re-run, meant to run against production immediately before `jobs/trello_ingest_job.py` first polls a newly-configured mebel department's real `trello_list_id` (see "Mebel module: Trello-first sync" above).

Production deploy target is **Railway** (`bot/railway.json`, NIXPACKS build, `python main.py` as a long-running polling worker — not a webhook, so no public URL/port needed). Deploy as its own service with Root Directory set to `bot/`; it reads env vars the same way locally (`config.Settings` via `.env`/`BASE_DIR`), so on Railway set `BOT_TOKEN`/`TRELLO_API_KEY`/`TRELLO_TOKEN`/`DATABASE_URL` as service environment variables instead (no `.env` file gets deployed — it's git-ignored).

## Architecture

### Layering (strict, one-way)

```
handlers/  → services/  → db/repositories/  → db/models/
              ↓
           trello/client.py
```

- **`db/models/`** — SQLAlchemy 2.0 `Mapped`/`mapped_column` models. All inherit `TimestampedBase` (`db/base.py`), which supplies `id`/`created_at`/`updated_at` — never redeclare these. Enums (`utils/enums.py`: `Role`, `TaskStatus`, `TaskType`) are stored `native_enum=False` (plain VARCHAR + no CHECK constraint) so adding a new enum value is a cheap additive migration, not a blocking `ALTER TYPE`.
- **`db/repositories/`** — one class per model extending `BaseRepository` (generic CRUD: `get_by_id`, `list_all`, `create`, `update`, `delete`). Repositories only `flush()`, never `commit()`. Add query methods here, not ad-hoc queries in services.
- **`services/`** — business logic, one module per concern (not classes — this is a deliberate, consistent choice across the codebase: `task_service`, `timer_service`, `penalty_service`, `notification_service`, `stats_service`, `settings_service`, `employee_service`, `registration_service`, `trello_sync_service`, `client_service`, `sales_service`). Each public function is its own **Unit of Work**: opens `async_session()`, does repository calls, `commit()`s, returns live ORM objects. This works safely because the session maker uses `expire_on_commit=False` (`core/database.py`) — returned objects stay readable after commit without a re-query.
- **`handlers/`** — aiogram routers. Deliberately tiny now: only `common/start.py` (`/start` — registration + a Mini App button, and a `StateFilter(None)` catch-all that redirects any other idle-state message to the Mini App) and `common/client_link.py` (`/mijoz` — clients aren't employees and can't open the Mini App, so this one flow stays chat-only). Every other role-specific flow that used to live under `handlers/admin/`, `handlers/worker/`, `handlers/brigadier/`, `handlers/sales/` has been fully ported into `miniapp/api/*.py` and those directories were deleted — see "Mini App" below. The "primary business call fails loud, secondary effects (notifications) are `try/except`-wrapped and logged-only" split still applies, just inside `miniapp/api/*.py` now.
- **`trello/client.py`** — thin `aiohttp` wrapper, `async with TrelloClient(...)`. Only implements what's actually used (boards, lists, cards, labels, list-move, members, checklists) — no comments or webhooks yet.

### Web panel (`web/`) — a separate app, not a client of `bot/`

`web/` is plain Node/Express with no framework and no build step (paths are `web/src/public/`, not `web/public/`). It cannot import `bot/`'s Python code, so anywhere its logic needs to match `bot/services/*.py` (`stats_service.py`'s monthly-stats query, and now `employee_service.py`'s create/validation rules), the logic is **hand-duplicated** in `web/src/routes/*.js` — if you change the grouping/filtering logic in `stats_service.py` or the validation/duplicate-check rules in `employee_service.py`, update the matching JS too, there's no shared source of truth to keep them in sync automatically.

- **Auth** (`web/src/auth.js`): one shared password (`WEB_ADMIN_PASSWORD`) compared with `crypto.timingSafeEqual`, no user table. Sessions are a stateless signed cookie (`HMAC-SHA256` over an expiry timestamp, keyed by `WEB_SESSION_SECRET`) — no session store, no extra dependency, survives server restarts by design.
- **Frontend** (`public/js/app.js`, vanilla JS, no framework): single-page "one window" layout per TZ §4.1 — the dashboard is one page; secondary views (ranking, employee-add) open in a **modal** rather than a route — reuse the existing `.modal`/`.modal-content` pattern for any new secondary view rather than adding page routing. Charts use Chart.js loaded from a CDN `<script>` tag, not an npm package.
- **Design system** (`public/css/style.css`): a real token system (`--surface-*`, `--ink*`, `--accent*`, `--positive`/`--critical`, etc.) defined once in `:root`, redefined under `@media (prefers-color-scheme: dark)` **and** `html[data-theme="dark"]`/`html[data-theme="light"]` (the toggle button in the topbar stamps `data-theme` on `<html>`, persisted to `localStorage`) — style new components through the tokens, never hardcoded hex, so both themes stay correct automatically. `--positive`/`--critical` (used by the stats-table chips and the score chart) are a **validated colorblind-safe pair** (`#008300` / `#e34948` light, `#008300` / `#e66767` dark) — don't swap these for "nicer-looking" green/red without re-running the dataviz skill's `validate_palette.js` (see Gotchas: an earlier green/red pair looked fine but failed the CVD check outright).
- **Employee-add** (`web/src/routes/employees.js` + `web/src/trello.js`): the one write path in `web/` besides login. `POST /api/employees` hand-duplicates `bot/services/employee_service.py`'s duplicate-name/phone checks and `employee_management.py`'s phone regex, plus computes `next_payment_date` itself (the 15th-of-month default is a Python model default, not a DB default — a raw SQL insert must set it explicitly or it lands `NULL`). `web/src/trello.js` mirrors `TrelloClient.get_member_id` using Node's built-in `fetch` (no HTTP client dependency). The form's single "Trello username or Gmail" field auto-detects by `@`: an `@` routes to `gmail` with no Trello lookup; anything else is looked up as a Trello username (404 → user-facing error, not silently accepted).
- A Telegram Mini App now exists (`bot/miniapp/`) — see the dedicated "Mini App" section below. This supersedes the earlier "no Mini App, deliberate choice" stance, and has since gone further: the bot is now **Mini-App-only** for every operational role — chat commands/inline keyboards for admin/worker/brigadier/seller flows were removed entirely, not kept as a parallel interface.
- Routes live under `/api/*` (`web/src/routes/`), each protected by the `requireAuth` middleware from `auth.js`.

### Mini App (`bot/miniapp/`) — the only operational UI now; chat is just the front door

A Telegram Mini App (WebView opened from an inline `web_app` button, `keyboards/miniapp_kb.build_miniapp_button()`, or the persistent Menu Button set in `main.py`) is now the **sole** interface for all six roles — every admin/worker/brigadier/seller flow that used to have a chat command or inline keyboard has been ported here and the old `handlers/admin/`, `handlers/worker/`, `handlers/brigadier/`, `handlers/sales/` directories (and their `states/*.py`/`keyboards/*_kb.py` support files) were deleted. Chat now only handles `/start` (registration + Mini App button) and `/mijoz` (client self-linking — clients aren't employees and can't open the Mini App); any other message gets a `StateFilter(None)` catch-all in `handlers/common/start.py` that just points at the Mini App button. Unlike `web/`, the Mini App is **not** a separate Node app: `bot/main.py` runs an `aiohttp.web` server (`miniapp/server.py`) *inside the same process* as the polling loop via `asyncio.gather()` — no new deploy target, no logic duplicated in a second language. Every endpoint calls the exact same `services/*.py` functions the old chat handlers used (`task_service`, `timer_service`, `penalty_service`, `employee_service`, `settings_service`, `sales_service`, `stats_service`) — the one deliberate exception to the "hand-duplicate in the other language" pattern `web/` established, chosen specifically because these are **write** paths with real side effects (Trello card moves, KPI penalties); duplicating that logic in JS was rejected as the highest-risk kind of divergence bug.

- **Auth**: Telegram WebApp `initData` (HMAC-SHA256, keyed by `SHA256(bot_token)` per Telegram's own spec) verified in `miniapp/auth.py`'s `auth_middleware`, sent by the frontend as an `X-Telegram-Init-Data` header on every `fetch()` (never as a URL param — Telegram doesn't append anything to the WebApp URL itself, the frontend reads `Telegram.WebApp.initData` client-side). Resolves to an `Employee` via `telegram_id` — the only identity check left in the system now that chat-side `RoleAccessMiddleware` is gone. Role-gating is done at the **sub-app** level, not per-handler decorators: `/api/miniapp/admin`, `/brigadier`, `/seller` are separate nested `aiohttp.web.Application`s each with their own `role_middleware(...)`, mounted under the parent `api_app` (which only requires "is an active employee") — `request["employee"]` set by the parent's `auth_middleware` propagates through to sub-app middlewares since it's the same `Request` object. `common`/`worker` routes carry no role gate — worker actions rely on task *assignment*, not role.
- **Resource-ownership checks are per-endpoint code, NOT automatic** — `auth_middleware`/`role_middleware` only prove "this is a real, active employee of role X"; they say nothing about whether the caller owns the specific `task_id`/`lead_id`/`employee_id` in the URL. A real-DB audit (2026-07-22) found several endpoints that skipped this and let any authenticated caller act on any other employee's records — since fixed, and now the required pattern for every new endpoint that takes a resource id: `miniapp/api/worker.py`'s `_is_assigned(task_id, employee_id)` gates `start`/`stop`/`resume`/`finish`/task-detail (a `common`/`worker` route reachable by any role, so the task-assignment check *is* the only authorization); `miniapp/api/brigadier.py`'s `_employee_in_scope()` restricts `/members/{employee_id}/...` to the requester's own brigade (BRIGADIER) or department (SUPERVISOR), and `_resolve_brigade()`'s `brigade_id` query param is likewise clamped to the requester's own department, not taken at face value; `miniapp/api/seller.py`'s `_own_lead()` restricts `/leads/{lead_id}/...` to `lead.assigned_seller_id == employee.id`; `miniapp/api/admin.py`'s `_department_scope_ok()` (added 2026-07-22, same audit family) restricts SUPERVISOR to their own department across ~10 endpoints there (employee list/detail/edit/toggle-active, task create/activate/reassign, brigadier/brigade lookups) — ADMIN stays unrestricted, and a department-less SUPERVISOR (global) is also unrestricted, mirroring `_resolve_brigade()`'s convention. When adding a new endpoint under an id path param, ask "could a different employee of the same allowed role pass a different id here" — if yes, it needs one of these checks or a new one shaped like them. `services/timer_service.py`'s `stop_task`/`resume_task`/`finish_task` additionally re-check the assignment themselves (an optional `employee_id` param — `None` for non-employee callers like `daily_sync_job`'s Trello-archive auto-close) as defense-in-depth beneath the API-layer check; `start_task` deliberately does **not** get this, since its job is to *attach* employee_ids to a task, not gate on pre-existing assignment.
- **Getting the `Bot` instance inside a handler**: use `request.config_dict["bot"]`, **never** `request.app["bot"]`. `app["bot"] = bot` is only ever set on the root `aiohttp.web.Application`, and aiohttp's `add_subapp()` does **not** chain state to child apps (no automatic inheritance at any depth) — `request.app` returns whichever (sub-)app owns the matched route, so for `/admin`, `/brigadier`, `/seller` handlers (two levels of subapp nesting) `request.app["bot"]` raises `KeyError` even though it happens to work for `common`/`worker` routes (one level, and only because `notify_task_started` etc. wrap it in `try/except` — the equivalent unwrapped `bot = request.app["bot"]` in `stop_task`/`finish_task` would 500). `request.config_dict` is aiohttp's built-in `ChainMapProxy` across every ancestor app in `match_info.apps` and is the only reliable way to read root-level state from arbitrarily nested sub-apps — found and fixed via the `_smoke_*` real-DB verification workflow (see Commands section), not by inspection.
- **Frontend** (`miniapp/public/`, vanilla JS/CSS, no build step, no framework): reuses the web panel's validated design tokens as a **static copy** (`public/css/app.css` — bot can't import `web/`'s CSS across languages) since Telegram WebApp messages can't be styled any other way. Navigation is two layers: a persistent **bottom tab-bar** (`#tabbar`, `tabDefsForRole()`/`renderTabBar()` in `app.js`, rendered fresh after every screen change) picks the active section per role (Worker: Buyurtmalar/Vazifalar/Ball/Profil; Admin/Supervisor: Bosh sahifa/Statistika/Xodimlar/Profil, with Sozlamalar reachable from Profil rather than as its own tab; Brigadier: Brigada/Profil; Seller: Lidlarim/Profil), and within a section a JS-side push/pop stack (`nav.stack`) drives Telegram's native `BackButton` for drill-down screens (task detail, employee edit, etc.) — `switchTab()` resets the stack, `show()`/`goBack()` push/pop within it, and `replaceTop()` re-renders the current top-of-stack entry in place (same screen, fresh data) **without** growing or wiping the stack — use this, not `show()`, for "refresh this same screen after an action" (e.g. after a toggle/save that isn't navigating anywhere) and not `resetTo()` for "switch what this screen displays" (e.g. the new-task form's Order/Misc segmented control) unless the screen is genuinely a tab root with nothing below it to preserve — a 2026-07-22 audit found ~15 call sites conflating these three and either corrupting the back-stack (`resetTo()` from a non-root screen silently drops its ancestors) or pushing duplicate/self-referential entries (`goBack()` immediately followed by `show()` of the very screen `goBack()` already re-rendered, or `show()` of the screen already on top). The primary action per screen is always Telegram's native `MainButton` (never an in-page "submit" button) — `setMainButton()`/`hideMainButton()` wrap it. Real per-screen dynamic content (task titles, employee names, department names) is **not** translated — only UI chrome (labels, statuses, buttons) is, via `public/js/i18n.js`'s `uz`/`ru` dictionary, because those are free text an admin typed in, not strings this system owns a translation for.
- **The full visual redesign (2026-07-28 plan) is implemented in code** (2026-07-28) — the premium-minimal direction (plan doc since deleted) is live: indigo/violet accent tokens (`#4f3ff0` light / `#8676ff` dark) replaced the old olive-green palette across `app.css`'s `:root`/`@media`/`[data-theme]` blocks, the emoji glyphs in `app.js` were replaced with an inline SVG line-icon sprite (`index.html`'s `<symbol id="ic-*">` defs, drawn via a small `icon(name)` helper) — except `setMainButton()` labels, which stay plain-text emoji since Telegram's native button can't render HTML — and a motion layer (`applyStagger()`/`animateNumbers()` wired centrally into `renderCurrent()`, a sliding tab-bar pill, slide/fade screen transitions) was added, all gated behind `prefers-reduced-motion`. Verified so far only via a mocked local server + headless screenshots (light/dark, two roles) — **still needs a real Telegram WebView check on-device** before this note (and the plan doc) can be considered fully closed out.
- **Sign→colour for any score/ball goes through `scoreClass()` / `heroTone()` / `scoreSigned()` in `app.js` — never write the ternary inline.** These three helpers were introduced 2026-07-28 because every screen had hand-rolled its own and several were wrong in ways that misinform the user about money: `.chart-head .big` (the worker's own monthly total) had `color: var(--positive)` hardcoded in CSS, so a **negative** month rendered green; three `hero-tile` call sites used `>= 0 ? "positive" : ""`, so a negative score fell through to plain body text instead of red (and `0` was painted green); and `.member-top .score.neg` shared a CSS rule with `.zero`, painting a brigade member's negative score neutral grey. Rules now: `> 0` → `--positive`, `< 0` → `--critical`, `== 0` → `--ink-soft` (neutral, **not** green). `heroTone()` returns the `hero-tile`'s own `positive`/`critical` vocabulary (that class is also used for non-score counts like "completed this month", which is why it wasn't collapsed into `scoreClass`). An overdue deadline tile is `critical`, not `warn` — `warn` means "due within a day", overdue is a different state.

- **Language preference**: `employees.language` (`a1c9f3e7d502` migration, default `'uz'`) — set from the Mini App's own Profile screen (`POST /me/language`), not from the chat (no bot command sets it). Switching it re-renders the *entire* app in that language, not just the Profile screen.

### Exceptions

Each service module defines its own exception classes (`TaskNotFoundError`, `InvalidTaskStateError`, `DepartmentNotConfiguredError`, `PenaltyRuleNotConfiguredError`, etc.) rather than sharing a common hierarchy. Handlers catch these by name and translate to user-facing Uzbek text; anything unexpected falls through to a generic `except Exception` + `logger.exception` + generic error message, so a bug never silently fails a Telegram interaction.

### Remaining chat FSM conventions

Only two `StatesGroup`s are left (`states/registration_states.py`, `states/client_states.py`) since every other multi-step flow moved into the Mini App's REST endpoints (no FSM there — each screen just does a fetch). `handlers/common/start.py`'s `StateFilter(None)` catch-all means any new chat `StatesGroup` **must** get its state-specific handlers registered before that catch-all would otherwise intercept free-text input meant for the new flow — mirror the existing `RegistrationStates`/`ClientLinkStates` pattern (state-specific handler in its own router, checked in `main.py`'s router-inclusion order) rather than adding raw `@router.message()` handlers with no state filter. This ordering rule bit a real feature once already: adding the (since-removed) `handlers/common/daily_report.py` without re-checking `main.py`'s router list left `common_start_router`'s catch-all registered *before* `common_client_link_router`, silently swallowing every `/mijoz` message from a fresh/idle user — found and fixed (2026-07-24) only by tracing aiogram's actual dispatch order, not by inspection. Re-verify this order any time a router is added or reordered.

- **The daily photo/video report feature (Fasad sex Phase 8) was fully removed from the code on 2026-07-31** at the user's request ("kunlik rasm/video umuman kerak emas"), so `/start` and `/mijoz` are now the *only* two chat flows. It used to be a third chat-only exception with a deliberately non-FSM, state-independent `F.photo | F.video` filter (a job has no `Dispatcher`/FSM-storage access, so it couldn't set chat state before prompting). That pattern is gone along with `handlers/common/daily_report.py`, `jobs/daily_report_job.py`, `services/daily_report_service.py`, and the submission model/repo. Removal was safe because the feature had **never been used in production** (0 submission rows, 0 employees flagged). Like the 8.6 removal below, it was **code-only**: `daily_report_submissions` plus the `employees.daily_report_required` / `app_settings.daily_report_time` columns still exist in the DB (both have a `server_default`, which is why dropping them from the models is safe) — dropping them needs a separate, explicitly-requested migration. If a genuinely stateful multi-step chat flow is ever needed, use the `RegistrationStates`/`ClientLinkStates` FSM approach, not the removed filter pattern.

- **Registration/client-linking is phone-verified via Telegram's own contact-share button, not typed text** (changed 2026-07-22, `services/registration_service.py`/`client_service.py`): both `waiting_for_contact` states only accept a `message.contact` (a `KeyboardButton(request_contact=True)`), never free-typed input — a plain-text message in that state gets re-prompted, it's never treated as a name or phone number. This replaced an earlier ism/typed-phone flow that let anyone claim a coworker's identity by typing their name. The handler also checks `message.contact.user_id == message.from_user.id` — some Telegram clients let a user attach a *different* contact card from their address book, so this rejects sharing someone else's number. Matching against the DB uses `EmployeeRepository`/`ClientRepository`'s `find_by_normalized_phone()` (via `utils/formatters.normalize_phone()`, last-9-digits comparison) rather than an exact string match, since admins type phone numbers in inconsistent formats (`+998...`/`998...`/spaced) when creating the record.

- Timezone: Tashkent is fixed UTC+5 (no DST) — hardcoded as `TASHKENT_TZ` in `utils/formatters.py`. Mini App deadlines are picked via `<input type="datetime-local">` and converted client-side (`app.js`) before being sent as ISO 8601 UTC; chat's old `DD.MM.YYYY HH:MM` local-time parsing is gone along with the handlers that did it.
- Worker task/score views (`GET /tasks`, `/misctasks`, `/score` in `miniapp/api/worker.py`) are split by `TaskType` the same way the old `/tasks`/`/misctasks`/`/myscore` commands were — `ORDER` and `MISC` never merge in one list, and score uses `penalty_service.month_bounds()` + `KpiLogRepository.list_by_employee_in_range()`, newest-first.

### Production task lifecycle (the core domain model)

A `tasks` row is either `task_type=order` (backed by a real Trello card) or `task_type=misc` (a Trello-free ad-hoc assignment, `trello_card_id` always NULL). Orders move through a **chain of departments** (mebel is `Shpon → Shkurka → Kraska`), each hop being its own `tasks` row:

- `departments.next_department_id` (self-FK) defines the standard pipeline; `NULL` = final stage.
- `tasks.previous_task_id` (self-FK) chains a stage back to its predecessor; multiple stage-rows share the same `trello_card_id` (not unique — only *one* non-`COMPLETED` row per card is "current" at a time, an app-level invariant, not a DB constraint).
- Finishing a stage (`timer_service.finish_task`) is deliberately **not** where stage-advancement happens — `task_service.advance_task_stage()` is called separately, only from the worker's "Yakunlash" handler, never from `finish_task` itself or from `daily_sync_job`'s Trello-archive-triggered auto-close path (archiving a card means the *whole order* terminated, not "advance to next stage" — conflating these two was a real bug caught during development).
- A new stage starts life as `status=PENDING_SETUP`, waiting on **two** things: a deadline and an assignee. Which of those the system fills in itself depends on the module:
  - **mebel** — neither. `deadline` stays `NULL` until a supervisor/admin enters it (`activate_pending_stage`). (In practice mebel ORDERs no longer go through `PENDING_SETUP` at all — `sync_trello_card_stage` creates them directly `ACTIVE` with the deadline read off the Trello card.)
  - **fasad_sex** — the **deadline is pre-computed** from `departments.default_sla_hours` at the moment the order enters the stage (`task_service.resolve_stage_deadline()`, SPEC.md §5.1), so the clock runs from the real hand-off, not from whenever a supervisor got around to tapping the button. The stage still sits in `PENDING_SETUP` because the *assignee* is still missing; `activate_pending_stage(deadline=None)` keeps the pre-computed value. 20 of the 23 `fasad_sex` departments have real SLA hours set (the other three are terminal/"no deadline" stages), so this is the live path, not a dormant feature.
  `jobs/daily_sync_job.py` excludes `PENDING_SETUP` rows from its open-tasks scan in both modules.
- Trello card membership and the "Bosqichlar" checklist track the same chain: `task_service.create_task()` adds assigned employees as real card members (via `employees.trello_member_id`, resolved once at employee-creation time) and creates one checklist item per department in the chain; `advance_task_stage()` checks off the just-finished department and drops its employees from the card; `activate_pending_stage()` re-adds the new stage's employees. All of this is a secondary effect (logged on failure, never blocks the primary DB write).
- **Assignment is two-stage, not direct-to-worker**: `create_task()`/`activate_pending_stage()` are still generic (`employee_ids: list[int]`), but the Mini App now always calls them with a **single** id — the department's brigadier (picked via `GET /admin/departments/{id}/brigadiers`, `miniapp/api/admin.py`), never a worker directly. The brigadier is therefore the sole `task_assignments` row and the deadline clock runs against them. `notify_task_started` pings the brigadier to open the Mini App; there they see the task in their "🆕 Yangi ish" queue (`GET /brigadier/pending-delegation`) and call `POST /brigadier/tasks/{id}/delegate` (`task_service.delegate_task()`) to hand it to specific worker(s) from **their own brigade only** (`EmployeeRepository.list_by_brigade`, enforced in `miniapp/api/brigadier.py` before the service call) — this fully replaces the brigadier's `task_assignments` row with the chosen worker(s), the same "no partial/co-assignment, full handoff" rule `reassign_task_brigade()` already used. `notify_task_started` fires again for the newly-assigned worker(s). The brigadier keeps earning their `brigade_share_ratio` KPI cut regardless (`penalty_service` derives it from `brigades.brigadier_id`, not from `task_assignments` membership). Because a brigadier's own `employees.brigade_id` is set to the very brigade they lead (see the circular-FK gotcha below), `stats_service.get_brigade_monthly_stats()` returns the brigadier alongside their workers in one list — `miniapp/api/brigadier.py`'s `/brigade` endpoint doesn't separate them, so the Mini App frontend (`screenBrigadierHome()`) splits the brigadier's own record out by `employee_id` to show it as a distinct score tile rather than one more member-card.
- **Who gets scored is "the workers, or failing that the brigadier" — never nobody.** `penalty_service._write_scores_for_employees()` picks the responsible party in two steps: if the assignee set contains any `Role.WORKER` they are scored (plus the 8.4-band brigade share to their brigadier, as before); if it contains **no** worker, the `Role.BRIGADIER` assignees are scored the **full** amount with no share on top. Before 2026-07-28 the second case wrote nothing at all, which mattered because *every* mebel stage starts brigadier-only (`sync_trello_card_stage` assigns the brigadier) — so a brigadier who simply never added a worker to the Trello card put the task permanently outside the KPI system, for themselves and everyone else. Roles other than WORKER/BRIGADIER are never scored in either branch. Two guards keep double-penalising impossible: the share step is skipped for non-WORKER, and `_apply_brigade_share_for_worker` already returns `None` when `brigade.brigadier_id == worker.id`. `bot/tests/test_penalty_responsible.py` pins all of this (plain `python tests/test_penalty_responsible.py` — no pytest, no DB, fake repos).
- **Only `task_service.ASSIGNABLE_ROLES` (WORKER, BRIGADIER) can become a task assignee from a Trello card** — both `sync_trello_card_stage()` and `trello_ingest_job`'s steady-state member-diff filter on it. Without the filter, any active employee with a `trello_member_id` who happened to be a card member became the assignee; a real ADMIN account had done exactly that on production task #129, and since admins are never scored, that task sat silently outside the KPI system. Being on a Trello card is not the same as being assigned the work.
- **Writing a KPI log and telling the employee about it are two different things — `penalty_service.notify_kpi_logs(bot, kpi_logs)` is the single helper that does the second, and every path that writes KPI logs must call it.** Added 2026-07-28 after a real bug: KPI scores were being written correctly but two of the four paths never notified anyone, so workers were penalized silently. The paths and how they get it: `finalize_task_and_apply_penalty()` (the "finish + penalty + notify + swallow-and-log every failure mode" wrapper — used by `daily_sync_job`, `trello_ingest_job`, and now `claim_service.approve_claim`) calls it internally; `miniapp/api/worker.py`'s fasad_sex finish calls it directly after `calculate_and_apply_task_penalty()`; `task_service.reassign_task_brigade(..., bot=...)` calls it for the 8.3-band immediate old-brigade penalty. **`calculate_and_apply_task_penalty()` and `apply_penalty_for_employees()` never notify on their own** — they have no `Bot` handle by design, so calling either one directly means you own the notification. `notify_kpi_logs` no-ops silently on `bot=None` (seed/smoke scripts).
- **`claim_service.approve_claim` routes FINISH through `finalize_task_and_apply_penalty(bot, ..., finished_at=claimed_at, employee_id=...)`, not through `finish_task` + `calculate_and_apply_task_penalty` by hand** (changed 2026-07-28). Doing it by hand had two real consequences: the worker was never told their ball changed, and a `PenaltyRuleNotConfiguredError` (lateness past the last bracket) propagated out of the endpoint as a 500 *after* the task was already `COMPLETED` — leaving the claim `PENDING` forever, invisible to both the review queue (which filters out COMPLETED tasks) and the stale-claim reminder job (same filter). The wrapper swallows-and-logs all three failure modes, so approval always resolves the claim. `employee_id` is threaded through so `finish_task`'s defense-in-depth assignment check isn't lost.
- **`stats_service.KPI_ROLES = (WORKER, BRIGADIER)`** (added 2026-07-22) is the "who actually earns KPI" list used to filter `get_monthly_stats()`'s results for anything KPI-facing — the dashboard's `avg_score`/`top_performer` tiles and the full `/admin/stats` ranking (`miniapp/api/admin.py`) both filter through it. `get_monthly_stats()` itself stays **unfiltered** (all active employees, any role) because it also backs the dashboard's plain "faol xodim" headcount tile, which should include admins/sellers/etc. — don't add a role filter inside `get_monthly_stats()` itself, filter at the call site with `KPI_ROLES` instead, or you'll silently shrink that headcount tile too.
- `jobs/overdue_watch_job.py` runs hourly (alongside `daily_sync_job.py`'s daily Trello-label sync) and owns **six** independent phases, each wrapped in its own `try/except` so one failure can't stop the rest: (1) the deadline-approaching warning — window is `app_settings.deadline_warning_hours` for `fasad_sex`, a fixed 24h for mebel; (2) flipping tasks past their deadline to `OVERDUE`; (3) repeat overdue reminders every `overdue_repeat_hours` (`fasad_sex` only); (4) signaling tasks overdue by 48h+ for manual brigade reassignment, for departments with `auto_reassign_after_48h=True`; (5) auto-resuming `STOPPED` stages whose department sets `stopped_auto_resume_after_hours`; (6) stale-claim escalation at +2h/+6h/+24h (mebel only). If you add a phase, register it in `run()` with the same swallow-and-log shape and extend the summary log line. The actual brigade swap is always a human decision (Mini App's "🔁 Ko'rib chiqish kutilmoqda" queue, `miniapp/api/admin.py`'s `reassign_task` → `task_service.reassign_task_brigade()`), which penalizes the old brigade immediately and stamps `tasks.reassigned_at` so the eventual completion penalty is computed from that timestamp instead of the original `deadline` (no double-penalizing the new brigade for time it didn't own).
- **Stop/Finish are available for `OVERDUE` tasks, not just `ACTIVE`** (fixed 2026-07-27, a real gap — a worker had no way to act on a task once it flipped to `OVERDUE`): `timer_service.stop_task()`'s status guard is `(ACTIVE, OVERDUE)`, and `miniapp/public/js/app.js`'s `screenTaskDetail()` renders the Stop button/Finish `MainButton` for either status. `finish_task()` never needed this — it already allowed any non-`COMPLETED` status. This applies to fasad_sex and any worker-facing task view; mebel's own worker view has no action buttons at all regardless of status (see below).
- **Fork/join (Fasad sex extension)**: `next_department_id` above describes the linear case only. A department can instead be a **fork point** — `department_fork_targets` (`department_id` → N `target_department_id` rows) lets `advance_task_stage()` spawn multiple parallel branch tasks from one completed stage, all sharing `previous_task_id` (no `fork_root_task_id` column exists — sibling lookup assumes each branch is exactly one department deep before rejoining, see the `# ponytail:` comment at the sibling-query call site for the upgrade path if that stops holding) and the same `trello_card_id`. A department can also be a **join point** (`requires_join=True`): `advance_task_stage()` won't create its task until every sibling branch (found via that shared `previous_task_id`) is `COMPLETED` — until then it returns `None` for each branch that finishes early, same as "order complete" returns `None`, so a `None` result is now ambiguous between the two (check `department.requires_join` if the distinction matters at a call site). Because of this, **`advance_task_stage()`'s return type is `Task | list[Task] | None`**, not just `Task | None` — every caller must handle the list case. The Trello card deliberately stays in the fork-point's list for the whole fork duration (a card can't be in 3 lists at once) and only moves once, at join-fire, to the join department's list — per-branch progress is visible via the "Bosqichlar" checklist (rewritten as a BFS over `_collect_department_chain_names()` to handle the fan-out/fan-in shape; produces identical output to the old linear walk when there's no fork) and the DB, not card position. Known gap: join-fire is not idempotent under a genuine two-worker race (both finishing the last two branches near-simultaneously could each spawn a join task) — a real fork/join chain exists since 2026-07-24 ("Fayl yig'ish" → 3 branches → "Korpus sexi"), but no production exposure yet since no employees are assigned to it, tracked in `.claude/nazorat-trello/04-texnik-qarz-topilmalar.md`.

### Mebel module: Trello-first sync + claim-gated KPI (merged 2026-07-27)

Scoped strictly to `departments.module == "mebel"` (displayed in the Mini App's module chooser as **"Fasad seh"** — not to be confused with the department *literally named* "Fasad seh" inside this same module's chain, or with the unrelated `fasad_sex`/"Nazorat Trello" module above; this naming collision has confused the team more than once, including mid-conversation). `fasad_sex` is completely untouched by this — same shared engine (`task_service`, `timer_service`, `penalty_service`), every change here is a `module == "mebel"` guard at the call site, not a rewrite. When touching `task_service.py`'s card-mutation helpers (`_add_members_to_card`/`_remove_members_from_card`/`_create_stage_checklist`) or `timer_service.py`'s stop-list-move helpers, grep for `"mebel"` across `bot/services/`/`bot/jobs/` to find every gated spot before assuming a new Trello-write call site needs a new guard.

- **Trello is the only place a mebel ORDER task/stage gets created, advanced, or reassigned — the bot never writes to Trello for this module.** `jobs/trello_ingest_job.py` (5-minute `"interval"` trigger, the only non-`"cron"` job in this codebase) reads one **whole board** and classifies every list on it *by name* each poll. **No Trello list id is stored for mebel anywhere** (`departments.trello_list_id` is unused by this module — it is a fasad_sex-only column now): the only configuration is `app_settings.mebel_trello_board_id` plus `departments.trello_list_keywords` (comma-separated, e.g. Kraska = `"kraska,malyarka"`). See the dedicated section below for why.
- **List classification lives in `services/trello_board_map.py`** and runs on every poll, so the board is the source of truth: a **queue marker** in the name wins first (`QUEUE_MARKERS` — "hali boshlanmadik", "hali tasdiqlanmadi", "chiqqan", "dastavka", "ustanovka", "bitkan", …), otherwise a department keyword match makes it that department's **work** list, and anything unrecognised falls back to `QUEUE` so an unknown list can never silently start work. Consequences that matter: a newly-added brigade list ("Sardor shpon brigada 48 soat") is picked up on the next poll with zero configuration, a deleted list simply stops appearing, and swapping the Trello account/token only requires updating the one board-id setting. `bot/tests/test_trello_board_map.py` pins all 25 real board list names against their expected classification — **run it after touching the markers or keywords**, since a bad rule silently turns a work list into a queue (no error, work just never starts).
- **Card-in-list semantics drive the whole lifecycle** (this replaced a `next_department_id`-driven state machine): a card in a **work** list starts/continues that department's stage; a card seen in **any queue list** means it left the work list, so the open task for that card is auto-finished through `penalty_service.finalize_task_and_apply_penalty()` (scores + notifies). `sync_trello_card_stage()` creates the row **directly `ACTIVE`** (no `PENDING_SETUP`), and `next_department_id` is now informational for mebel — physical card movement, not the configured chain, decides what happens next. Mini App finish claims still work alongside this (early finish before the card moves). **Out of scope**: fork/join — a Trello card can't be in three lists at once.
- **Deadlines come from Trello, never from the DB**: the card's own `due` wins; failing that, the **hours parsed out of the list name** (`"kraska ELYOR 72 soat"` → now + 72h, via `trello_board_map.parse_hours`); failing both, no task is created and the card waits (logged). This is deliberate — the user sets durations by renaming lists in Trello, so there is no per-list duration column to keep in sync.
- **`app_settings.mebel_ingest_start_at` is the go-live cutoff.** Cards whose `dateLastActivity` predates it are skipped entirely. Without it, pointing at a real board floods the system: the production board had ~118 open cards that were already past due, each of which would have become an `ACTIVE` task, flipped `OVERDUE` on the next hourly job, and eventually charged a penalty for lateness that predates the system. A card rejoins the flow the moment it is touched in Trello (moved, member added), since that refreshes `dateLastActivity`.
- **Assignment from brigadier to worker also happens in Trello, not the Mini App** (changed 2026-07-27, superseding the fasad_sex-style `delegate_task()` picker for this module): a brigadier adds the specific worker(s) as card members directly in Trello; the ingest job's steady-state member-diff (`_sync_open_task` in `jobs/trello_ingest_job.py`) detects the change and calls `set_assignees_from_trello()` (full `task_assignments` replacement, same semantics as `delegate_task()`). **It takes a list — every resolvable worker on the card is assigned and notified**, because a brigadier splits one job across several workers; assigning only the first (the pre-2026-07-28 behaviour) left the rest with no task and no message. Then `notify_task_started()` goes to the new assignees and `notification_service.notify_task_delegated_via_trello()` to whoever was previously assigned (confirms their Trello action was picked up). `miniapp/api/brigadier.py`'s `POST /tasks/{id}/delegate` now 409s for mebel tasks — the Mini App's "🆕 Yangi ish" queue (`screenNewWork` in `app.js`) shows a "assign via Trello" hint instead of the worker-picker for mebel items, fasad_sex unchanged.
- **A worker's own Mini App has no Pause/Finish for mebel tasks at all** (changed 2026-07-27) — `screenTaskDetail()` shows task info (and a pending-claim banner, if one exists) only, never a Stop button or Finish/Resume `MainButton`, and `miniapp/api/worker.py`'s `/pause-claim`/`finish-claim` (not just the legacy `/stop`/`/finish`) now 409 for mebel too. Instead, **the brigadier submits Pause/Finish on the worker's behalf** from a new drill-down: `screenMemberTasks` (brigadier's per-member task list) → tap a task → `screenMemberTaskDetail` — calling `miniapp/api/brigadier.py`'s `POST /members/{employee_id}/tasks/{task_id}/pause-claim`/`finish-claim` (scoped by `_employee_in_scope` + a same-file `_is_member_assigned` check: the target worker must be in the brigadier's own brigade AND actually assigned to that task). - **Brigades are never created by hand — `employee_service.sync_brigade_links()` owns them** (2026-07-29). There is no "create brigade" screen or endpoint; saving an employee whose role is BRIGADIER get-or-creates one brigade per department they lead (`"{Department} — {Full name}"`, the name is deliberately readable since it appears in notifications), sets the brigadier's own `employees.brigade_id`, and links every brigade-less WORKER in that department. Dropping one nulls `brigadier_id` but **never deletes the brigade** (KPI history hangs off it); a later brigadier for that department adopts the orphan rather than creating a second brigade. Demoting someone out of BRIGADIER releases their brigades automatically. Consequence for callers: `BrigadeRepository.list_by_brigadier_id()` returns a **list** (was `get_by_brigadier_id()`, which crashed with `MultipleResultsFound` the moment a second brigade existed), and `miniapp/api/brigadier.py`'s `_resolve_brigade`/`_employee_in_scope` work across all of a brigadier's brigades — `GET /brigadier/brigade` accepts `?brigade_id=` and returns `brigades` (the picker) plus `own_score` (computed from the brigadier's own KPI logs, brigade-independent — `employees.brigade_id` can only point at one of them).
- **A worker's Pause/Finish/Resume claim doesn't take effect until a department SUPERVISOR/ADMIN approves it.** Resume joined the claim-gated set on 2026-07-29 (`ClaimActionType.RESUME` — no migration, the column is `native_enum=False`): the brigadier's `POST /members/{id}/tasks/{tid}/resume-claim` replaced an endpoint that used to resume immediately, and the worker's own `POST /tasks/{id}/resume` now 409s for mebel like stop/finish already did. All three action labels come from `notification_service.CLAIM_ACTION_LABELS` / `app.js`'s `CLAIM_PENDING_KEYS`/`CLAIM_ACTION_KEYS` — never re-introduce a two-way ternary, a third action already broke that pattern once. `services/claim_service.py`'s `approve_claim` is the only place `timer_service.finish_task`/`stop_task` actually runs for these, and it passes `claim.claimed_at` — **never** the approval time — into `finished_at`/`stopped_at`, so `penalty_service`'s KPI math is identical no matter how long the claim sat waiting for review. `reject_claim` does the opposite: zero task mutation, the task stays whatever it already was — a claim rejected days later resolves itself for free once the task is eventually really finished, no special-cased "rejection penalty" exists or should be added. Only SUPERVISOR/ADMIN can approve/reject (`miniapp/api/admin.py`'s `/pending-claims`, `/claims/{id}/approve`/`reject`, same `_department_scope_ok` pattern) — a brigadier is notified (`notify_claim_submitted`) but has no approve/reject endpoint, by design (their own action is submitting the claim itself, per the point above). `approve_claim` treats a task that moved on without the claim (archived-complete via the ingest job, or flipped `OVERDUE`) as a resolved-not-error outcome: it still marks the claim `APPROVED` and logs a warning rather than leaving it stuck `PENDING` forever.
- **Stale-claim escalation**: `jobs/overdue_watch_job.py`'s `_process_stale_claims` phase reminds the brigadier + SUPERVISOR/ADMIN at +2h/+6h/+24h of `claimed_at` (`TaskClaim.last_reminder_stage` prevents re-sending the same stage), skipping claims whose task already reached `COMPLETED`.

### Settings: three different mechanisms, don't confuse them

- `app_settings` (singleton table, `services/settings_service.py`, in-process cached) — scalar knobs: `default_penalty_multiplier`, `brigade_share_ratio`, `balls_per_day_shift`, `plus_ball_per_day`, `plus_ball_max_days`, `report_time`, `lead_follow_up_threshold_days`, plus `reminder_schedule`: a JSON list of `{"time": "HH:MM", "urgency": "info"|"warning"|"urgent"}` entries so the daily reminder can escalate through the day. Scalars are edited via the Mini App's Sozlamalar screen (`GET/POST /admin/settings`, `miniapp/api/admin.py`); the reminder list has its own `GET/POST/PUT/DELETE /admin/reminders` CRUD there. Any change to `reminder_schedule` calls `jobs/reminder_job.schedule_all()` (and any change to `report_time` calls `jobs/report_job.schedule_all()`), which tears down and re-registers the corresponding APScheduler jobs to match — job count always mirrors current settings, don't assume a fixed set of job ids.
- `penalty_rules` table — the actual late-penalty bracket schedule (variable number of `[min_hours_late, max_hours_late) → score` rows, optionally department-specific, global fallback via `department_id IS NULL`). Adding a new bracket is a data change, not a schema/code change. An hours-late value not covered by any rule raises `PenaltyRuleNotConfiguredError` — it deliberately does **not** fall back to the nearest known bracket. Brackets currently start at 0h (`[0,24)→-1 … [72,96)→-8`), no grace period — 2026-07-29, aligned to the sales department's forwarded official policy ("72 o'tgandan keyin har 24 soat uchun -1 ball..."), which penalizes from the moment the deadline passes, not after an extra free day. There *was* a code-level 24h grace period (`hours_late < 24` → no penalty) that silently shifted every bracket a full day later than the policy intended — removed from `penalty_service.calculate_and_apply_task_penalty`, and the bracket boundaries shifted down 24h to match (same scores, `[24,48)→-1` became `[0,24)→-1`, etc.). **The top bracket must always be open-ended (`max_hours_late IS NULL`)** — `[96,∞)→-12` closes a real production hole: an earlier cut of this table stopped at a fixed upper bound, so any task far enough late silently earned *no penalty at all* (the "no fallback to the nearest bracket" rule above is deliberate, but it means a missing top bracket is a silent gap, not a loud error, on the job paths — and on `reassign_task_brigade` it was a hard 500 instead). If you ever re-cut the bracket table, keep one row with `max_hours_late = NULL` or you re-open that hole.
- **`app_settings.sales_board_lists` still has no bot UI** — a JSON `{"ezza": {"new_lead": list_id, ...}, "melores": {...}}` map, configured by writing directly to the DB, not through a Telegram flow. Deliberate, not an oversight — don't build a settings UI for it without checking whether that's actually wanted. (`departments.trello_list_id` **did** get a UI on 2026-07-24 — the Mini App's department-edit screen, `screenDepartmentEdit` in `app.js` — so don't assume every Trello-list-id-shaped config field follows this DB-only pattern; check the specific field.)
- `BASE_PAYMENT_DAY = 15` in `penalty_service.py` is still a hardcoded constant pending business confirmation (not in the configurable list above). Check `shared/db-schema.md` before assuming a number is configurable.
- Fasad sex added `daily_quota_points_per_worker` (int, stats-display only — see `stats_service.get_capacity_vs_actual()`, never enforced as a penalty rule) to the same `app_settings` singleton, edited through the same `GET/POST /admin/settings` route. It also added `daily_report_time`, but that one is gone from `AppSettingsSnapshot` as of the 2026-07-31 daily-report removal (the DB column remains, unreferenced).

### Sales CRM (13-band, Phase 5) — a fully separate domain from `tasks`

`leads` (`db/models/lead.py`) and `call_logs` (`db/models/call_log.py`) are their own table pair, deliberately **not** built on `tasks`/`task_assignments`/`penalty_service` — leads have no deadline, no KPI penalty, no department chain. A lead belongs to a `brand` (`LeadBrand`: `ezza`/`melores`) and moves through a `stage` (`LeadStage`) via `services/sales_service.py`: `advance_lead_stage()` only steps forward through `NEW_LEAD → CONTACTED → OFFER_SENT → AGREED`; closing (`close_lead(won=...)`) can happen from any open stage straight to `CLOSED_WON`/`CLOSED_LOST` — both of those map to the same Trello list ("Yopildi"), since the TZ 6.1-band board only has 5 lists, not 6. Which Trello list a given `(brand, stage)` maps to comes from `app_settings.sales_board_lists` (see Settings section above) — not configured yet raises `SalesBoardNotConfiguredError`. Call logging (`sales_service.add_call_log`) is manual-only (typed into the Mini App's Lidlarim tab, `miniapp/api/seller.py`'s `POST /leads/{id}/calls`) and updates `leads.last_contacted_at`, which `jobs/lead_follow_up_job.py` (daily, 10:00) uses to nudge the assigned seller about stale open leads — re-sent every day the lead stays stale, not a one-shot signal. IP-telephony integration (an automatic call-log source) was explicitly scoped out — no provider was named in the TZ, and building a webhook receiver with nothing to receive from would be dead code; don't add one without confirming a provider first.

## Gotchas

- **The Trello "Test" board is not a clean sandbox** — discovered 2026-07-17: it contains at least one list with real-looking customer orders (e.g. specific names/addresses in card titles), not just throwaway test fixtures. Treat it as "don't touch, ambiguous provenance" rather than "safe to modify freely." For any new Trello-touching verification work, create a fresh dedicated board (`TrelloClient.create_board`) rather than assuming "Test" is empty/disposable — `bot/_seed_demo_data.py` does exactly this. **Exception, and the default target for Nazorat Trello work: "Nazorat Trello demo"** (`6a6b9b185fcbec9605db82a0`) — a card-less copy of the real `nazorat trello` board, and what the 23 `fasad_sex` departments now point at. Cards created there are safe to make and delete. The account holds several similarly-named boards; before writing, match the board by **exact name**, not by a substring — `Fasad seh`, `Fasad seh demo`, `Fasad sex — Ishlab chiqarish`, `Fasad sex — Ishlab chiqarish (DEMO)`, `nazorat trello` and `Nazorat Trello demo` all coexist, and only the last one is disposable.
- **`core/database.py`'s engine has `pool_pre_ping=True`** — added after a real incident where a `_seed_demo_data.py` run hung indefinitely mid-script with zero error output. Cause: Railway's Postgres proxy silently drops idle connections; without pre-ping, SQLAlchemy hands out a dead connection and the query just hangs forever (no timeout configured anywhere in the stack). Don't remove this to "simplify" the engine config.
- **Circular FK**: `brigades.brigadier_id` ↔ `employees.brigade_id`. Alembic autogenerate warns about an "unresolvable cycle" — harmless, ignore it. But when deleting test data, null out both FK columns before deleting rows, or you'll hit `ForeignKeyViolationError`.
- **Named constraints**: Alembic autogenerate sometimes emits `op.create_foreign_key(None, ...)` / unnamed unique constraints, which breaks `downgrade()`. Always give explicit names when hand-editing a migration (repo convention: `fk_<table>_<column>`).
- **New NOT NULL columns on non-empty tables** need a `server_default` in the migration or `alembic upgrade` fails.
- **`postgresql+asyncpg://`**: `DATABASE_URL` in `.env` is plain `postgresql://` (Railway's format); `config.settings.async_database_url` rewrites the scheme. Use `settings.async_database_url` for the engine, never `settings.database_url` directly.
- Trello card operations should generally happen **before** the corresponding DB write commits (see `task_service.create_task`'s docstring) — the failure mode to avoid is a DB row with no backing Trello card, not the reverse.
- **`web/` and `bot/` share one `.env`**: both `config.py` (`env_file=BASE_DIR/".env"`, where `BASE_DIR` is the repo root, not `bot/`) and `server.js` (`dotenv.config({ path: '../.env' })`, relative to `web/`'s cwd) resolve to the same root-level `.env` — don't create a second `.env` inside `web/` or `bot/`, it won't be picked up.
- **`web/src/routes/stats.js` duplicates `stats_service.py` SQL by hand** (see "Web panel" above) — a stats/KPI logic change on the Python side silently goes stale on the dashboard unless you update both.
- **`web.json_response(dict)` doesn't serialize `datetime` — a raw `datetime` field in the response dict 500s, silently, from a bare `TypeError` with no repo-specific error handling around it.** Bit for real in `miniapp/api/admin.py`'s `GET/POST /admin/settings`: those two handlers build their response from `AppSettingsSnapshot`'s fields generically (`{field: getattr(snapshot, field) for field in _SETTING_FIELDS}`), so when `mebel_ingest_start_at` (a `datetime`) got a real value, the endpoint 500'd for every caller until `_serialize_setting()` (`.isoformat()` if `isinstance(value, datetime)`) was added. Every other datetime-returning endpoint in this file already converted by hand — these two just iterate generically and missed it. Any future settings field of a non-JSON-native type needs the same treatment.
- **Don't eyeball chart/status colors — validate them.** A green/red pair chosen by eye for the web dashboard (score chips, chart bars) looked fine but measured ΔE 4–5 on a deuteranopia (red-green colorblind) check — a hard fail, not a style nit. Use the `dataviz` skill's `scripts/validate_palette.js` before shipping any categorical/status color pair; the current `--positive`/`--critical` tokens in `web/src/public/css/style.css` are the validated result.
- **Headless Edge screenshot QA (Windows) can silently fail to load CDN scripts** (e.g. Chart.js) under its default/reused profile — Edge's "Tracking Prevention" blocks jsdelivr, leaving the page half-rendered with no thrown error visible in a plain screenshot. If a headless verification screenshot looks suspiciously faded/blank, rerun with a fresh `--user-data-dir` before assuming the code is broken.
- **`msedge --headless=new --window-size=W,H` does not reliably render at `W` CSS pixels** — observed `window.innerWidth` coming back ~100px wider than the requested `--window-size` value, with no error or warning. A screenshot taken against an assumed width can make correctly-laid-out elements look like they're overflowing the viewport when they aren't. Before concluding a Mini App layout bug from a headless screenshot, inject a script that reports `window.innerWidth`/`getBoundingClientRect()` for the suspect elements (or `console.log` + read devtools) rather than trusting the requested `--window-size` — this cost real time chasing a phantom overflow bug that didn't exist at the actual rendered width.
- **Telegram's Mini App WebView caches static files aggressively** — after a real Railway redeploy (confirmed live in the dashboard), a user still saw the old `app.js` until fully force-closing and reopening Telegram; a background/foreground switch wasn't enough. **Fixed 2026-07-31**: `miniapp/server.py`'s `no_cache_middleware` (mounted on the root app) sets `Cache-Control: no-cache` on every response — static files, `index.html`, and `/api/miniapp/*` JSON alike. `no-cache`, not `no-store`, so `FileResponse`'s `ETag`/`Last-Modified` still yield cheap `304`s on unchanged files. Pinned by `bot/tests/test_miniapp_cache_headers.py` (no DB, no Telegram — spins the real app on localhost). If you add another static mount, the middleware covers it automatically; don't hand-set `Cache-Control` per handler unless you need something other than `no-cache` (the middleware uses `setdefault`, so an explicit value wins).
- **`jobs/trello_ingest_job.py` has no feature flag — its off-switch is data.** It returns immediately when `app_settings.mebel_trello_board_id` is empty or when no mebel department has `trello_list_keywords` set. That is the safe state to leave it in while reconfiguring. Note that a real board plus a registered worker is all it takes to start creating tasks, so set `mebel_ingest_start_at` *before* registering workers, not after. (`bot/_backfill_mebel_trello_tracking.py` predates the name-based rewrite and backfills the `trello_last_seen_*` columns for the old per-department-list flow — it is harmless but no longer part of mebel rollout.)
- **`settings_service.AppSettingsSnapshot` is a frozen dataclass that lists its fields explicitly** — adding a column to `db/models/app_setting.py` is *not* enough, the snapshot and `_load_from_db()` must be updated too or the value is simply invisible at runtime. This bit for real: the new mebel board settings were read with `getattr(app_settings, "...", None)`, so the missing field silently resolved to `None` and the ingest job did nothing at all while appearing to run fine. Read new settings as plain attributes so a missing field raises instead of disappearing.
- **"Fasad seh demo" (formerly "Melores Mebel — DEMO") is a real, sizeable clone of production, not throwaway seed data** — 2026-07-27, a one-off script copied every currently-open list/card/checklist/comment (read-only) from the actual production board `https://trello.com/b/2ErITeBO/fasad-seh` (which itself has 433 lists/3044 cards once archived history is counted — the copy deliberately only took the ~26 open lists/~540 open cards that actually landed, since ~731 open cards turned out to live in lists Trello no longer has any record of at all, 404 on lookup, not just archived). Card *members* were deliberately **not** copied — replicating them would have required adding the board's 20 real employees to the demo board, which sends a real Trello notification. Don't assume this board's card volume/realistic-looking order titles mean it's production, and don't assume a card's member list reflects anything from the real board (every card here starts unassigned).
